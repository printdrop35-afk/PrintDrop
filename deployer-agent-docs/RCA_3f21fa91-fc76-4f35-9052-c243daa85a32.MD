# RCA — printdrop.fr: staff get "Fichier supprimé" / "Document supprimé" (410/404) instead of the PDF

## Problem statement
Staff open / click "Imprimer" on a customer-submitted document in the dashboard and receive
"Fichier supprimé" / "Document supprimé" (HTTP 410 on the dashboard, 404 on the agent) instead
of the PDF — for documents that should still be available.

## Verdict
CONFIRMED. The backend stores uploaded files on **local container disk** (`STORAGE_DIR`), which is
**ephemeral and per-pod**. With 2 replicas and frequent redeploys, uploaded files are routinely
lost — present on neither the image nor the pod that serves the read — so `Path.read_bytes()`
raises `FileNotFoundError` and the endpoints return the "Fichier supprimé" error. This is a
code/architecture issue; it is NOT a secret, tier, or platform fault.

## Evidence

### 1. STORAGE_DIR points at ephemeral container filesystem
- `list_secrets`: `STORAGE_DIR` is set and matches `/app/backend/storage_private`.
- `lib/storage.py`: `STORAGE_DIR = Path(os.environ.get("STORAGE_DIR", "/app/backend/storage_private")).resolve()`;
  `save_file()` does `path.write_bytes(data)` to local disk; reads use `resolve(key).read_bytes()`.
- This path is inside the container's writable layer. The FARM template mounts **no persistent
  volume**; tier shows only `ephemeral_storage: 1Gi` (scratch, not durable). Files written at
  runtime do not survive a pod replacement and are not shared between pods.

### 2. Two replicas on two different nodes, no shared storage
- `get_tier`: `replicas: 2, max_replicas: 2`.
- `get_pod_events`: both pods (…-cnsgl, …-x5fbq) scheduled to **different nodes**
  (i-02562a178326c6239 and i-062160c56e2c27478), each with its own local disk.
- Consequence: an upload POST handled by pod A writes to pod A's disk; a later read routed to
  pod B finds nothing → `FileNotFoundError`. Intermittent by design (depends on routing).

### 3. Frequent redeploys wipe the disk
- `describe_deployment_state`: 5 successful redeploys on 2026-11-09 between 15:58 and 17:39.
- Current pods started 2026-11-09T17:38:58 (restart_count 0) — fresh filesystem containing only
  the image's baked files. Every redeploy loses all runtime uploads written since the last build.

### 4. Logs show the exact failing endpoint + error code
- `fetch_app_logs`: `GET /api/orders/7e91931d…/documents/dd8833bc…/file?variant=print` → **410 Gone**
  (both inline and attachment). Status histogram over the window: 410 ×2, plus 404s (the 191 "404"
  are `GET /health` probe noise against a route the app doesn't expose — unrelated).

### 5. Code paths that produce the user-visible messages
- `routers/dashboard.py` `document_file` (GET /api/orders/{order_id}/documents/{doc_id}/file):
  - line 273-274: `status == "purged"` or no `storage_key` → **410 "Document supprimé après le retrait de la commande"**
  - line 276-278: `resolve(doc["storage_key"]).read_bytes()` in try/except → on exception → **410 "Fichier supprimé"** (this is the FileNotFoundError / missing-file path)
- `routers/agent.py` `job_file` (GET /api/agent/jobs/{job_id}/file):
  - line 205-206: no `storage_key` → **404 "Document supprimé"**
  - line 208-210: `read_bytes()` in try/except → on exception → **404 "Fichier supprimé"**
- So "Fichier supprimé" is specifically the disk-read-failed path on a document that is STILL
  `attached`/`uploaded` with a non-null `storage_key`.

### 6. Mongo ⟷ disk mismatch proven directly
- `documents` collection: **114** docs with `status != "purged"` AND non-null `storage_key`
  (vs only 5 `purged`). These all expect a file on disk.
- The active, currently-uploading org is `d17a9824-5245-49d2-8435-6ab49b145d67` (shop `raos-aa3e`,
  seen POSTing documents with 200 OK in logs; recent docs a8482ab2 / d6a2eaa9 point there).
- Inspected the baked image contents (eph sandbox = exact source baked into the running image):
  451 files are baked, but the **entire `d17a9824…` org directory is absent** from the image, and
  its real upload keys are **MISSING**:
    - `d17a9824…/27bb627d…/88bf0efa95d044809a89959c6181a2de.pdf` → MISSING  (doc a8482ab2, status=uploaded, created today 17:48)
    - `d17a9824…/27bb627d…/742112c287024952856a53b6868f2c39.pdf` → MISSING  (doc c1ab239c, status=attached)
  - By contrast a committed seed/demo key `d19437ef…/…/5bd9453246…pdf` IS present — only because it
    was committed to the repo and baked into the image. Real customer uploads never are.
  This is the proof: Mongo says the document is live with a storage_key, but the file does not
  exist in the running image and was not preserved across the redeploys → `read_bytes` fails →
  "Fichier supprimé".

### 7. The 410 "purged" cases are mostly legitimate — with one risk
- The 5 `purged` docs were purged 1–17 min after creation by `lib/retention.py` when their orders
  reached `picked_up`/`cancelled` (dashboard.py line 224 calls purge on those transitions) — this
  is intended behaviour (files deleted once an order is finished).
- RISK to flag: `retention._erase_documents` uses `resolve(key).unlink(missing_ok=True)`. When the
  disk has been wiped, the file is already gone, `unlink` "succeeds", and the doc is marked
  `status=purged, storage_key=None`. So a file lost to ephemeral storage can be silently recorded
  as a deliberate purge, destroying evidence and the recovery path. This masks data loss.

## Root cause
Uploaded documents are persisted to the pod's local, ephemeral filesystem (`STORAGE_DIR`) instead
of durable, shared storage. With 2 replicas and no shared volume, a read can hit a pod that never
received the upload; and every redeploy/pod-restart discards all runtime uploads. Either case makes
`read_bytes()` raise `FileNotFoundError`, surfaced to staff as "Fichier supprimé" (410 dashboard /
404 agent). Files already lost this way are also being silently finalised as "purged" by the
retention job.

## What is NOT the cause
- Not a secret problem (STORAGE_DIR is set correctly to the documented default).
- Not a tier/OOM/resource problem (pods healthy, running, restart_count 0; raising the tier would
  not make local disk durable or shared).
- Not a platform/pipeline fault — the deploys succeeded and the app serves.

## Suggested fix (Code — E1)
1. Replace local-disk storage in `backend/lib/storage.py` with **durable, shared storage** reachable
   by every replica and surviving redeploys. Options, best first:
   - Object storage (S3 / Cloudflare R2 / GCS) via a signed-URL or stream-through read; OR
   - MongoDB GridFS (already have Mongo, survives redeploys, shared across pods).
   `save_file`, `resolve`/read, and `delete_file` all move to that backend; keep the HMAC-signed
   short-lived link model.
2. Fix `lib/retention.py::_erase_documents` so a **missing file is not treated as a successful
   purge** — distinguish "deleted by us" from "already gone"; do not null `storage_key`/set
   `status=purged` when the object was simply not found, so genuine loss is detectable and not masked.
3. Data note: documents created before the migration whose files lived only on ephemeral disk are
   already lost and cannot be recovered from the app side; affected customers must re-upload. The
   114 non-purged docs with storage_keys are suspect — only those whose keys exist in the baked
   image (seed/demo data) will still open.

Interim mitigation (does not fix root cause): running a single replica reduces the cross-pod miss,
but redeploys/restarts still wipe uploads — not a real fix. The durable-storage migration is required.
